# ADR-0011: OpenTargets GraphQL client design
Date: 2026-05-18
Status: Accepted (§1.3 — Cowork-decides engineering choice)

## Context

OpenTargets is the primary evidence-aggregation source for this repo's
dossiers (per ADR-0008). The client must support three properties that
together make results reproducible: response caching, platform-version
pinning, and bounded-retry behavior. None of these touch biology.

## Options considered

### Retry policy
- **A1: No retries.** Fragile — OT is occasionally slow and returns 5xx.
- **A2: Unbounded exponential backoff.** Risks hanging the pipeline
  forever on a sustained outage.
- **A3: Bounded retries (3 attempts; 1s/2s/4s delays) via tenacity.**

### Cache strategy
- **B1: No cache.** Re-runs hit the live API. Wastes network and
  introduces non-determinism when OT updates.
- **B2: HTTP-spec cache (e.g., hishel).** Respects server cache headers.
  OT's cache headers are imperfect; we'd be at their mercy.
- **B3: Content-addressed cache keyed by SHA256(method + url +
  canonicalized-body).** Deterministic; survives across runs; doesn't
  depend on server headers.

### Version pinning
- **C1: No pinning.** OT updates change scores; old results become
  irreproducible.
- **C2: Pin the platform release at client construction time.** Read
  `meta { dataVersion { ... } }` once; record the version in every
  cached response; refuse to use a cached response from a different
  version unless the caller explicitly opts in.

### Caching API responses to disk
- Cache directory: `$XDG_CACHE_HOME/pd_target_credentialing/opentargets/`
  with files named by SHA256 hash of the request signature.

## Decision

- **A3: Bounded 3-attempt retries via tenacity** with 1s/2s/4s
  exponential backoff. After 3 failures, raise `OpenTargetsError` with
  the upstream HTTP status.
- **B3: Content-addressed on-disk cache.** Cache hit returns instantly;
  cache miss issues live request, caches response, returns it.
- **C2: Pin platform version at client construction.** Version becomes
  part of every cache key (so a re-run after an OT update doesn't
  silently use mixed-version data).

## Consequences

- HTTP layer uses `httpx` (sync for now; async-ready interface for the
  Repo 5 agent reuse later).
- `respx` is the test-time mocking layer.
- Every cached response stamps the platform release version on disk, so
  audit trails are intact.
- The retry/cache code lives in the shared `_http/` package and is
  reused by the Reactome client (ADR-0012).
